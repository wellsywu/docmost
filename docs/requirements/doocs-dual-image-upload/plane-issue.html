背景

目标流程不是在 Docmost 本地附件与 Doocs 图床之间二选一，而是一次粘贴完成双写：先复用 Docmost 原生附件能力，把图片写入当前部署配置的 Local/S3/Azure Storage 并绑定页面；再按工作区 Doocs 设置，把同一图片上传到微信公众号或 Doocs 专用 S3，生成发布 URL。

源 Docmost 页面应继续引用受附件生命周期管理的 /api/files/{attachmentId}/...；复制到微信或其他发布输出时使用微信/S3 的公开 URL。详细分析和方案见 docs/requirements/doocs-dual-image-upload/。

当前差距

  • Docmost 原生粘贴通过 /files/upload、AttachmentService 和当前 Storage driver 创建附件记录。
  • Doocs 集成粘贴直接调用 /integrations/doocs/upload，当前按配置只上传微信或 S3并返回外部 URL，不创建 Docmost 附件。
  • 现有复制资产转换只修改最终 HTML 副本；DOCMOST-42/43 明确不负责 Doocs 粘贴图片的附件双写。
  • 粘贴前校验还把 docmost provider 误判为缺少本地图床配置，因此会弹出“本地上传”窗口。

  A-->>D: attachmentId 和附件 URL
  D->>P: 按工作区 Doocs 设置上传同一图片
  P-->>D: 发布 URL 或可重试错误
  D-->>E: attachment 与 publishAsset
  E->>E: 源 Markdown 插入附件 URL
  E->>E: 复制发布时使用 publish URL

改造方向

  1. 由 Doocs 服务端上传端点统一编排双写，图片只从浏览器上传一次，Secret 不下发浏览器。
  2. 复用 Docmost 附件域的路径、Storage driver、数据库记录、权限和审计逻辑；不要从服务端反向请求 HTTP /files/upload。
  3. 增加以 attachmentId 为键的发布资产映射和重试状态，按 workspace、provider、公众号账号或 S3 配置版本隔离。
  4. Doocs 插入 Docmost 附件 URL并保存回源文档；复制 HTML 时读取映射并替换为微信/S3 URL。
  5. 修复 Markdown 写回后的 attachmentId 恢复，避免只剩 URL 而丢失 Docmost 附件身份。

验收标准

  • 在 Doocs 中粘贴、拖入或选择一张图片时不再打开“本地上传”配置弹窗，浏览器只提交一次图片文件。
  • 上传成功后，Docmost 主库存在绑定当前页面的 attachment 记录，文件实际进入部署配置的 Local/S3/Azure Storage。
  • 同一图片同时按工作区 Doocs 设置上传到选中公众号或 Doocs S3，并获得真实外部 URL；不得用 Docmost 本地 URL冒充发布 URL。
  • Doocs Markdown 与保存回 Docmost 的源内容引用 Docmost 附件；复制到微信的最终 HTML 引用微信/S3 URL，且不包含 /api/files/。
  • 保存回 Docmost 后图片节点仍能恢复正确 attachmentId，重新打开、复制页面和删除页面的附件生命周期正常。
  • Docmost 附件写入失败时不写发布图床；发布图床失败时保留 Docmost 图片、显示可重试状态，并在复制发布前重试或阻断坏内容。
  • 只读/过期会话不能创建附件；公众号、S3 配置、附件和发布映射均按 workspace 隔离。
  • AppSecret 与 S3 Secret 不出现在浏览器响应、Doocs storage 或日志中。

不在范围内

  • 不把 Doocs 图床配置替换成 Docmost 全局 Storage 配置。
  • 不把微信 CDN URL作为 Docmost 页面唯一内容源。
  • 不承诺跨 Docmost Storage 与外部图床的分布式原子事务。
